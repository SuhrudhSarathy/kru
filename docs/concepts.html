How it works

The design behind kru, for the curious and for contributors.

On-disk layout

<store dir>/
├── state.json          # active bucket; device-local, not synced
├── buckets/
│   └── <bucket id>.json   # one file per bucket, with its tasks
├── notes/
│   └── <task id>.md       # markdown notes (plain buckets only)
├── tombstones.json     # what was deleted, and when (for sync)
├── .lock               # held while saving
└── .git/, .gitignore, sync.log   # only once sync is set up

Find the directory with kru path. Everything is readable JSON (except private buckets, which are sealed), so you can back it up with any tool.

Identity: ids vs numbers

Every task and bucket has a UUID that never changes. The number you see (#3) is just its position in the display order, computed on the fly, which is why numbers shift. Sync, notes and scripts all key on ids.

Format versioning

Every file records its format version and the kru release that wrote it. When a file is read it is upgraded step by step in memory and written back in the current format on the next save. A file from a newer kru is refused instead of misread, so upgrade kru rather than editing data by hand.

Concurrent access

Saves take a lock on the store, re-read what's on disk and merge in whatever another process saved meanwhile. A CLI call never undoes what an open TUI did, or the other way round.

Retention

  • Done tasks are pruned when kru starts, after 7 days.
  • Tombstones (records of deletions) are kept 90 days. A device that hasn't synced for longer may bring a task that was deleted elsewhere back.

Why git for sync

Git already gives transport, authentication, history and hosting for free, and kru's data is small text files. kru adds the part git can't do for this data: a structured, id-based three-way merge, so two devices editing different fields of one task never produce a conflict marker. See Syncing.

Code map

PathResponsibility
src/store/The store: loading, saving, locking, migrations, notes, tombstones, private buckets
src/task.rs, src/bucket.rsThe data types and their fields
src/privacy.rsKey derivation and sealing of private buckets
src/sync/Git wrapper, snapshots and the three-way merge
src/cli/Commands, argument parsing, text and JSON output, completion
src/tui/Event mapping, app state and rendering (ratatui)

The CLI and TUI both go through the same Store methods, so they behave identically.
